## 1. 测试目标和工作方式

目标是发现会影响接单决定的错误：漏掉订单、把两单合成一单、误算薪资、把频率当成星期、错误放行或排除订单，以及配置丢失、批处理崩溃和敏感信息外发。

参考专业测试工作的流程：先明确业务规则和风险，给用例写人工预期，再进行自动化和页面验证，最后交付可复现的缺陷与发布建议。用等价分类选代表输入，用边界值检查临界位置，用条件组合检查筛选规则，用状态切换检查页面和配置。这些方法参考 [ISTQB CTFL v4.0.1 第4、5章](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)；以下优先级、样本规模和验收目标是针对本项目的建议。

本项目有两种必须核对的结果：

- 字段是否正确：原文中的年级、科目、报价、星期、频率、时长、方式和教师要求是否被正确表达。
- 接单决定是否正确：在指定接单条件下，订单应明确匹配、可能匹配、无法解析，还是应被排除。

预期结果由业务语义人工标注，不用程序自己的解析结果生成“标准答案”。保留失败证据，避免为了让测试通过而改变用例预期。

## 2. 测试对象与环境

测试对象为当前工作目录中的完整版本，包含上次提交后尚未提交的识别优化。执行前记录 Git 提交号、工作区改动摘要和依赖版本，保证结果可以对应到具体代码。

计划环境：Windows、项目 `.venv`、Python 3.12、Streamlit 和 pytest。浏览器以电脑端为主；手机窄屏进行基础布局检查。

目前已有自动化用例是回归资产。上一轮曾报告80项通过，正式执行时重新统计；不把上一轮结果记作本轮结果，也不据此宣称真实订单准确率。

测试输入采用模拟或脱敏订单。自动化配置保存测试使用临时目录和模拟密钥。实际浏览器验证采用临时测试副本、独立端口和模拟配置，避免测试过程改写日常使用的配置与订单。

## 3. 风险优先级

| 优先级 | 本项目含义 | 典型风险 |
|---|---|---|
| P0 | 无法继续使用或暴露敏感信息 | 整批崩溃、原文丢失、API Key进入导出/日志、完整个人联系方式或详细地址进入模型请求 |
| P1 | 接单决定明显错误 | 时薪换算错误、错误明确匹配、应保留的订单被排除、订单漏切/误切、配置重启后丢失 |
| P2 | 信息可用但有明显缺陷 | 字段来源解释不清、范围展示误导、页面或导出内容与操作名称不一致 |
| P3 | 低影响体验问题 | 文案、间距、窄屏排版等 |

先覆盖P0/P1，再补充体验检查。疑似问题在执行前只是待验证风险，复现后才登记为缺陷。

## 4. 确定业务预期

| 规则 | 正确预期 |
|---|---|
| 跨维度筛选 | 所有已知条件都必须满足；一个已知硬条件不符即可排除 |
| 同一维度多选 | 年级、科目等选项按已确认规则满足其一即可 |
| 固定上课日 | 所有要求的固定日期均应在教师可接星期中 |
| 明确的备选安排 | “周六晚上或周日上午”按完整备选分支判断，至少一个分支可接才保留 |
| 最低时薪边界 | 150元/小时在最低150元时应通过，149.99元应不通过 |
| 全部报价已知 | 合并为最低到最高时薪；全部低于门槛则排除，范围跨门槛则可能匹配，全部达到门槛则薪资条件通过 |
| 存在未确定报价 | 保留已知范围并待确认，不能把已知最高价当成整个订单的最高价 |
| 未注明时段 | 不能把“一次3小时”推断成上午、下午或晚上 |
| 频率与星期 | “一周一次”是频率，不表示周一；“每周三次”也不表示周三 |
| 模型故障 | 单条失败保留原文并继续处理；模型不能直接决定最终匹配状态 |
| 身份和去重 | 每条订单独立内部ID，地址和外部编号重复不能导致丢单 |

以下需求细节在执行报告中单列，不自行添加产品规则：

- “导出全部”指全批订单还是当前筛选下的全部可见订单。先核对页面文案、原规格与实际导出，再给出结论。
- 多个薪资分别绑定不同上课方式时，当前已确认的全订单薪资范围仍作为基础规则；更精细的“方式—薪资”关联筛选列为待确认增强项。
- “数理化”等别名允许涉及哪些科目；不明确的边界记录为规则待确认，不能直接算成已证实的程序错误。

## 6. 数据集与自动化方法

### 人工标准答案

首轮计划约50条人工标注的合成/脱敏订单：常规字段、薪资变化、时间逻辑、边界切分、缺失/歧义各约10条。模型异常回复单独用故障用例构造，不混入订单识别准确率。

每条标注保留原文、预期订单数、各字段、指定条件和预期状态。不明确的业务语义标记为“规则待确认”。这批是开发验证集，不能代表真实订单分布；后续真实脱敏订单的验收集应单独标注和保留，避免一边调规则一边宣称泛化准确率。

### 测试工具

- 本地业务：pytest参数化，检查字段、边界和筛选结果。
- 性质检查：固定随机种子生成组合，验证“报价顺序改变范围不变”“提高最低时薪不增加候选订单”“已知单价对应的课费与课时同时倍增，时薪不变”等业务性质。
- 接口异常：Mock模拟响应和SDK异常，统计调用次数与批次输出；不把Mock成功计入真实模型准确率。
- 页面行为：优先使用 [Streamlit AppTest](https://docs.streamlit.io/develop/api-reference/app-testing)，模拟输入、导航、确认和重启会话。
- 浏览器验收：补充真实TXT选择、点击区域、下载、窄屏和实际重新启动。无法真实操作的项目报告为未验证。

既有用例先复用，再补缺口。测试数量和覆盖率是辅助指标，最终需要检查高风险业务是否真正有独立预期和复现证据。

## 7. 执行顺序（用户确认后）

| 阶段 | 操作 | 产出 |
|---|---|---|
| 1 | 固定代码快照，核对需求与人工预期 | 环境记录、规则待确认清单 |
| 2 | 运行既有回归，记录原始结果 | 现状基线 |
| 3 | 建立标注样例，补边界、组合和性质检查 | 新用例及映射表 |
| 4 | 执行模型故障、脱敏、导出、配置测试 | 通过/失败证据与缺陷列表 |
| 5 | 执行页面自动化、浏览器验收、300条本地批次 | 页面记录与本地性能数据 |
| 6（可选） | 小规模真实模型核验 | 单独的模型质量与耗时记录 |
| 7 | 汇总、复核失败、给出修复优先级 | 测试报告与发布建议 |

默认首轮以离线、Mock和隔离页面环境执行。可选真实模型阶段使用合成/脱敏订单，最多10次逻辑解析调用；现有SDK重试可能使HTTP请求达到最多20次。模型切分调用也计入这一预算。是否执行该阶段随本方案一并由用户确认；不进行300条真实API压力调用。

执行阶段先报告发现的问题与复现方法。产品修复作为后续工作安排；修复后运行失败用例和受影响的回归用例，不把修复后的结果覆盖掉初次失败记录。

## 8. 统计与验收建议

报告列出通过、失败、预期失败、跳过和未验证；记录失败用例、时间、代码快照和运行命令。任何预期失败都作为尚未解决的问题，不能算成通过。

| 指标 | 统计方式 |
|---|---|
| 切分正确率 | 整批订单数量与边界均正确的批次 / 可判定批次 |
| 字段正确率 | 按年级、科目、时薪范围、星期、频率、时长分别统计正确/可判定数量 |
| 最终状态正确率 | 对照人工条件表，统计正确状态 / 可判定订单 |
| 错误明确匹配 | 实际显示明确匹配、人工判断不应明确匹配的数量，单独列出 |
| 错误排除 | 应保留的订单被程序排除的数量，单独列出 |
| 容错表现 | 各故障类型是否保留原文并完成批次；是否有崩溃 |
| 性能 | 本地三轮耗时、结果规模；小样本在线耗时独立列出 |

建议验收条件：P0/P1核心用例全部通过；无已确认但未解决的P0/P1缺陷；样例不丢单、不错误确定放行；脱敏与密钥隔离检查通过。P2/P3列清单处理。

50条开发验证集与少量真实接口调用不足以证明“真实准确率达标”。首轮重点是找出并复现缺陷；真实准确率目标需在独立标注集上评估。300条本地处理的耗时先测基线，再决定性能门槛，不用本地耗时推断模型在线处理时间。
